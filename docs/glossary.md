# Glossary

The canonical vocabulary for the coding agent. When code, docs, specs, or conversation use a domain concept, use the term as it appears here. PRs that introduce or rename a domain concept update this file in the same change.

The seed rows below are taken directly from the project architecture; fill `Notes` and add rows as each step lands.

| Term | Definition | Notes |
|---|---|---|
| **Harness** | The runtime wrapper around the agent loop: message queue, priority gate, and the wiring to TUI, sandbox, hooks, and services. | The whole running system minus the model itself. |
| **Agent Loop** | The Pydantic-AI ReAct loop that alternates between the LLM and tool calls until the task is done. | Also called the "React Loop". One loop per turn. |
| **Priority Gate** | The check between loop iterations that injects newly-arrived user messages from the queue into the running loop. | Lets the user steer mid-run without restarting. Realised by the two queues below (Steering + Follow-up). |
| **Steering** | A mid-turn user line, drained from the steering queue *before each model-request leg* and injected as a user message, so the model sees it on the next leg (never mid-stream/mid-tool). | Plain `Enter` while a turn is busy (ADR-0002 §4). Contrast Follow-up. |
| **Follow-up** | A queued user line drained *only at the would-stop boundary*, continuing the conversation as one more turn-leg once the current turn would otherwise stop. | `Alt+Enter` while busy (`InputIntent.FOLLOW_UP`). Contrast Steering. |
| **Decision Channel** | The single mid-turn input surface (`DecisionChannel`): when a turn must ask the human before continuing, the requester awaits a future on this channel and the main input loop routes the next typed line into it. | One decision pending at a time (single-flight); avoids a second `prompt_async()` deadlock (ADR-0002 §3-4). Serves both Deferred Approval and AskUser. |
| **Deferred Approval** | The ask-on-every-tool permission step: a gated tool raises `ApprovalRequired`, the run resolves to a `DeferredToolRequests` pause, and the human's allow/deny (via the Decision Channel) resolves it before the tool executes. | The deferred-tool mechanism that also enables mid-turn steering (ADR-0002 §2-3). |
| **AskUser** | The one blocking, *ungated* tool: the agent asks the human a free-form question mid-turn and the typed answer becomes the tool result. | Rides the Decision Channel, not the permission gate (gating it would double-prompt) — ADR-0002 §7. |
| **Sandbox** | The execution environment for Bash/tool side effects — `local` (Docker/Firecracker) or `remote` (Modal), behind one `run` seam. | The one deliberate infrastructure abstraction (see ADR). |
| **Services Interface** | The boundary exposing LLM Gateway, Memory, LSP servers, and MCP servers to the agent. | Distinct from `tools/` (what the model calls). |
| **Compaction** | The context-engineering feature that shrinks a long conversation as a cheapest-first, **window-relative** cascade driven by provider-reported **input** tokens vs `compaction_context_window_tokens`: **Microcompaction** (cheap, no-LLM, in-memory) elides old tool-output bodies once usage reaches `window*(1 - microcompaction_reserve_fraction)` (~60% full); **full Compaction** (one LLM call) summarizes older history into a fixed Markdown skeleton plus a recent verbatim tail snapped to a Compaction Boundary once usage reaches `window*(1 - compaction_reserve_fraction)` (~80% full) or on manual `/compact`. Full compaction is persisted as a typed `compaction` checkpoint line on the append-only JSONL session log (NO SQLite); replay reconstructs the compacted history. | Two automatic triggers + manual `/compact`; `compaction_enabled` gates the automatic cascade. Invariant `microcompaction_reserve_fraction > compaction_reserve_fraction` (micro fires first). Successive full compactions merge for free. Distinct from the on-exit one-sentence memory write-back, though all grew from the same summary seam (ADR-0006). |
| **Compaction Boundary** | The turn boundary the kept verbatim tail is snapped to during full Compaction — the start of a user turn (a `ModelRequest` carrying a `UserPromptPart`) — so a compaction never cuts mid-tool-call/mid-tool-result and never leaves an orphaned tool result the model would reject. | `compaction_keep_recent_tokens` chooses *how much* tail to keep; the Compaction Boundary chooses *where* the cut may legally land (ADR-0006 §5). Microcompaction reuses it only to delimit "old" — it never removes parts, so it cannot orphan a pair. |
| **Microcompaction** | The cheap, no-LLM, **in-memory** compaction tier: blanks the *bodies* of `ToolReturnPart`/`RetryPromptPart` in messages older than the kept recent tail with a placeholder (`"[tool output elided by microcompaction]"`), only replacing content — never removing messages — so it can never orphan a tool-call/result pair. Idempotent. | Fires when input usage is between the micro line (`window*(1 - microcompaction_reserve_fraction)`, ~60%) and the full line (~80%). **Not persisted** — the JSONL log keeps full fidelity; resume replays full history and re-microcompacts. The cheaper tier below full Compaction (ADR-0006 §3a). |
| **Memory Compression** | The second compaction level: when the model-maintained `MEMORY.md` reaches its **200-line** cap (`memory_max_lines`), one cheap LLM call dedupes/merges the highest-signal facts and rewrites the file under the caps, instead of the old drop-oldest trim — which remains the guaranteed fallback/ceiling when the call fails or is disabled. | Runs on exit in `extract_on_exit` after the dated-bullet append, gated by `memory_compression_enabled`; fully non-fatal. Reuses `memory_max_lines`/`memory_max_bytes`; no new caps (ADR-0006 §8). |
| **Context Gauge** | The TUI footer fill indicator: a pie-fill circle `○ ◔ ◑ ◕ ●` plus a percentage showing `last_input_tokens / compaction_context_window_tokens`, colored green / yellow / red by the same tier fill lines (below ~60%, ~60–80%, at/above ~80%) so the user sees the context approach Compaction. | Pure `tui/render.py::context_gauge` helper, footer-wired in `tui/app.py`, reading the handler's public `last_input_tokens`. Uses the same window setting as Compaction (single source of truth). `○◔◑◕●` is the portable terminal approximation of a fill ring (ADR-0006 §9). |
| **Subagent** | A child agent spawned by the main agent via the Agent tool; runs a scoped task and returns a compressed result. | From the Agents Catalog (Build/Plan/Explore/Code-Reviewer). |
| **Skill** | A reusable instruction unit stored as a **directory** `<name>/SKILL.md` — `name` + `description` YAML frontmatter and a Markdown body of guidance — loaded on demand by the model (the Skill Dispatcher `skill(name)` tool) or the user (the TUI `/<skill-name>` command). A project skill's directory may also ship optional **Bundled Resources** (sibling folders/files). Built-in skills ship packaged under `decode/skills/builtin/<name>/SKILL.md` (SKILL.md-only); project-local skills live at `<cwd>/.decode/skills/<name>/SKILL.md`, are keyed by their frontmatter `name` (the directory name is cosmetic), and override a built-in of the same name. | Pure injected instructions, **not** executable code (M3). No tools/mode fields and no body-size cap; the actions a skill *describes* still pass through their own tool gates — e.g. the built-in `commit` skill's `git add`/`git commit` run via the gated `bash` tool (ADR-0004 §7). |
| **SKILL.md** | The single canonical entry file of a Skill directory: `---`-fenced YAML frontmatter (`name` + `description`) followed by the Markdown instruction body. It is the **only** file a built-in skill ships, and the required file the loader looks for in each `<name>/` directory (a subdirectory without one is skipped). | The on-disk form of a skill (ADR-0004 §3). The skill's identity is the frontmatter `name`, not the directory name (a dir-name ≠ `name` mismatch still loads but logs a WARNING). |
| **Bundled Resources** | The optional sibling files/folders (`references/`, `examples/`, `scripts/`, or any others) shipped alongside a **project** skill's `SKILL.md` and loaded on demand (tier 3 of Progressive Disclosure): the SKILL.md body references them by relative path and the model loads them via the `read` tool (or runs `scripts/` via `bash`). | A **project-skill** feature only — built-ins are SKILL.md-only, since their files would live unreadably in site-packages (ADR-0004 §3). Surfaced to the model by the Skill Dispatcher's resource **trailer**, appended only when present; `SkillDef.resource_dir` points at the directory iff it holds anything besides `SKILL.md`. |
| **Skills Catalog** | The lightweight index of every available Skill — each skill's `name` + one-line `description` — injected into the system prompt by a dynamic `@agent.instructions` hook so it is always present but cheap. | The "menu"; the full body is fetched only on demand (see Progressive Disclosure). An empty catalog contributes no prompt text, like an empty memory block (ADR-0004). |
| **Skill Dispatcher** | The ungated `skill(name)` tool: given a skill name it returns that skill's full `SKILL.md` body as the tool result — plus a short resource **trailer** naming the skill's directory when the skill has Bundled Resources (tier 3); an unknown name raises `ModelRetry` listing the available skills. | The model's entry point (the user's is the `/<skill-name>` TUI command); both share one `format_skill_payload` helper so the payload never diverges. Ungated like `ask_user`/`sleep` — loading instructions has no side effect — and hidden unless the active agent lists `skill` in its `tools` (ADR-0004 §7). |
| **Progressive Disclosure** | The **three-tier** skill-loading strategy: (1) the cheap Skills Catalog (names + descriptions) is always in the prompt; (2) a skill's full `SKILL.md` body is loaded only when invoked — by the model via the Skill Dispatcher or by the user via `/<skill-name>`; (3) a project skill's Bundled Resources are loaded only when the model follows the body and reads them by relative path (`read`/`bash`), with the directory surfaced by the dispatcher's resource trailer. | Keeps token cost low — each tier is paid for only when reached (ADR-0004). Tier 3 is project-skill-only; built-ins stop at tier 2. |
| **Permission Mode** | The gate's evaluation mode — one of `default`, `plan`, `edit`, `bypass` — that, with the tool's Tool Kind and any matching Permission Rule, decides allow/ask/deny for a tool call. | Replaces M1's single `ask` mode (ADR-0003 §1). Mutable on the gate; cycled by Shift+Tab. |
| **Default Mode** | Permission Mode where read-only tools auto-allow and mutating tools ask the human. | The startup default (ADR-0003 §1). |
| **Plan Mode** | Permission Mode where read-only tools auto-allow and every mutating tool is denied with a reason telling the model to present its plan and call `exit_plan_mode`. | Entered via `enter_plan_mode`, `/mode plan`, or the `plan` agent (ADR-0003 §1,8). |
| **Edit Mode** | Permission Mode where read-only and file-edit tools (`write`/`edit`) auto-allow but other mutating tools (`bash`) ask. | a.k.a. acceptEdits; `exit_plan_mode` lands here on approval (ADR-0003 §1,8). |
| **Bypass Mode** | Permission Mode where every tool call is allowed with no prompt. | No human gate — use with care (ADR-0003 §1). |
| **Tool Kind** | A tool's permission classification — `read_only`, `file_edit`, or `other` — declared once on its registry spec and read by the gate so Edit Mode can tell a file edit from a shell exec. | Replaces M1's single `read_only` bool (derived from it). `todo_write` is `read_only` (in-memory, no side effect) — ADR-0003 §2. |
| **Permission Rule** | An allow/deny entry of the form `Tool(pattern)` (or bare `Tool`), matched against the call's subject (bash→command, file→path, web→url). | Two sources: the user's optional `.decode/settings.json` and an agent's catalog frontmatter. Precedence: deny → allow → mode (ADR-0003 §3-4). The `always` answer persists a user allow rule. |
| **Agents Catalog** | The set of built-in agent personas (Build, Plan, Explore, Code-Reviewer), each a Markdown file with YAML frontmatter (name, description, tools allowlist, default mode, optional allow/deny rules) plus a system-prompt body, loaded and validated at startup. | Used as the main agent only this milestone — no subagent spawning (ADR-0003 §5). |
| **Agent (persona)** | One Agents Catalog entry: a validated `AgentDef` carrying the system prompt, the allowed tool set, optional agent-scoped rules, and the default Permission Mode the agent runs under. | Distinct from the Pydantic-AI `Agent` object; selecting one sets `deps.active_agent`, resets the gate mode, and loads its rules (ADR-0003 §5-7). |
| **EnterPlanMode / ExitPlanMode** | Model-callable tools that switch the gate into Plan Mode and back. `exit_plan_mode` asks the human to approve the plan (via the Decision Channel); on approval it switches to Edit Mode. | Ungated controls — they ride the Decision Channel, not the permission gate (ADR-0003 §8). |
| **LLM Provider** | The selectable inference backend that serves the agent loop's model requests — one of `gemini`, `openrouter`, or `modal` — chosen explicitly by the `LLM_PROVIDER` setting (no auto-detection), each with its own credentials and default model id. | Default `gemini` keeps existing `.env` files working (ADR-0005 §1). Distinct from the **Services Interface**'s "LLM Gateway" framing: this is the concrete config-selected backend the **Provider Seam** constructs. |
| **Provider Seam** | The `agent/factory._build_model()` helper that branches on the selected **LLM Provider** and returns the constructed Pydantic-AI model, while the rest of `build_agent()` (tools, hooks, `output_type`) stays provider-agnostic. | The realized form of the provider-swap seam ADR-0002 §1 deferred; filled by ADR-0005 §3. Gemini → `GoogleModel`; OpenRouter/Modal → `OpenAIChatModel`. Modal uses a custom `AsyncOpenAI` client: dual `Modal-Key`/`Modal-Secret` proxy-token headers when both tokens are set, or a plain `api_key="EMPTY"` client with no headers for an `--unauthenticated` endpoint (MODAL_MODELS.md §6). |
| **Code Intelligence** | The semantic understanding of source code — go-to-**definition**, find-**references**, **hover**, and **diagnostics** — that decode exposes for Python via a Language Server, delivered through two orthogonal channels: an **active** model-callable `lsp` tool and the **passive** Diagnostics Enricher (ADR-0007). | The "codebase as a semantic graph" view, complementing the "codebase as text" view of `read`/`grep`. Python-only this step; best-effort (absent/slow server → the agent falls back to text tools). |
| **Language Server** | The external process decode shells out to for Code Intelligence — `ty server` (Astral, same vendor as `ruff`/`uv`) by default — speaking LSP (JSON-RPC over stdio). Swappable via `lsp_server_command` / `lsp_server_args` (e.g. `pylsp`). | One per project root, lazily spawned. `ty` is pre-1.0 / preview, pinned by `uv.lock` (ADR-0007). decode uses the **pull** diagnostics model (request→response), never `publishDiagnostics` push. |
| **LSP Service** | decode's hand-rolled JSON-RPC-over-stdio **client** for one Language Server (`src/decode/services/lsp/`) — the first concrete entry behind the **Services Interface**. It frames `Content-Length` messages, runs the `initialize` handshake + `didOpen`, issues the four ops + a pull `diagnostic` request matched by id, and shuts the server down on exit. | Lazy, **one server per project root**, cached behind a module-level seam (mirrors bash's `_EXECUTOR`); a broken spawn is cached to avoid retry storms; **best-effort everywhere** (never throws into the loop). No protocol library — the wire is hand-rolled (ADR-0007). |
| **Diagnostics Enricher** | The **passive** Code Intelligence channel: after a successful `write`/`edit` on a `.py` file, an **errors-only** diagnostics summary is appended to the tool's return string so the model sees and fixes its mistakes inline. | Rides the edit's already-granted approval (no extra permission gate); silent on clean files and whenever the server is unavailable; gated by `lsp_diagnostics_on_edit` (and the master `lsp_enabled`). "The single best ROI of an LSP integration." Contrast the active `lsp` tool, which is the explicit query surface and reports all severities (ADR-0007). |
| **Headless Runtime** | The second, non-interactive entry path (`src/decode/runtime/`): a Kitaru **Durable Flow** that runs the same `build_agent()` autonomously via `KitaruAgent(...).run_sync(task)`, launched by `decode run "<task>"`. It bypasses the interactive `Runner`/`agent/loop.py` (no mid-turn Steering/Abort — those are interactive-only); it gets Kitaru **Replay**/**Wait** instead. | The "unattended single task" path that unblocks deploy (step 12) and the cloud PR reviewer (step 13). Coexists with — never replaces — the interactive TUI and its JSONL session log (ADR-0008). Master-gated by `runtime_enabled`. |
| **Durable Flow** | The Kitaru `@flow`-decorated function (`runtime/flow.py::run_agent_task`) that wraps the agent for the Headless Runtime. One flow = one autonomous task; **sync** (the adapter bridges the async pydantic-ai agent internally — no manual asyncio); launched via `flow.run(task).wait()`. | Kitaru is imported and called directly (no gateway wrapper) until a third surface forces one — the `runtime/` module is earned by being a genuine second caller of `build_agent()` (ADR-0008). |
| **Checkpoint** | The durable record Kitaru writes after a unit of agent work inside a Durable Flow — per agent turn under `checkpoint_strategy="turn"` (the MVP default, `runtime_checkpoint_strategy`), or per model/tool call under `"calls"`. On **Replay**, a finished Checkpoint returns from cache instead of re-running the model/tool. | "What the agent has already written down and cannot lose," distinct from the in-flight pydantic-ai loop. Coarsens to per-turn when streaming (ADR-0008). Not the same as the compaction `checkpoint` JSONL line (that is interactive-mode persistence). |
| **Replay** | Re-running a Durable Flow execution with already-finished Checkpoints served from cache: a crash resumes near the failure instead of from the top, a resolved **Wait** answer replays from its saved record, and a **what-if** replay re-executes the run from a chosen anchor with one flow input changed (e.g. a swapped **Model Override**) to see what *would* have happened. | The headless analogue of interactive `--resume`, now also the what-if engine (ADR-0008 §8, ADR-0010). `flow.replay(exec_id, from_=<cp>, model=…)` / `kitaru executions replay <id> --from <cp> --args … --overrides …`. Upstream of `from_` serves from cache; `from_` and downstream re-execute for real, so an override only bites downstream. On the local stack a **Wait** is re-asked on replay (answer-reuse needs a deployed stack — `tasks/future/`). |
| **Wait (HITL)** | A flow-scope durable pause (`kitaru.wait()` / the adapter's `wait_for_input`) that suspends a Durable Flow until an operator resolves it out-of-band (`kitaru executions input <id> --value …`), then resumes from the same point. In flow mode decode bridges **both** Decision Channel resolvers — permission approvals (`resolve_permission`) and `ask_user`/`exit_plan_mode` (`resolve_user_question`) — to a Wait. | The headless bridge of the interactive **Decision Channel** (one seam → one swap per mode). Each Wait has a stable name so Replay reuses the prior answer. Also backs the durable `sleep` timer (a one-shot `wait(timeout=…)`); Kitaru has no native cron (ADR-0008 §3-4,6). |
| **Secret-Store Config (Kitaru)** | Headless-only (`decode run`) hydration of config from a Kitaru secret via `get_secret(runtime_secret_name)`: the **model key** (`runtime_credentials_proxy_enabled`, task 061) and/or the **whole `.env.example` surface** (`runtime_secret_store_config`, task 064). Values land in the **`Settings` object only — never `os.environ`, never a worker env**; precedence **real env > Kitaru secret > `.env` > default**. | Honors "secrets never reach the model or the sandbox payload." Both opt-in, default off; the interactive REPL never reads the secret (or imports kitaru). The rule: *Kitaru secret → `Settings`, yes; → process/worker env, no* (ADR-0008 §5). |
| **Credential Proxy** | Kitaru's HTTP **header-injection** proxy for a sandboxed worker's outbound *tool* credentials — `SandboxProxyRule` (per-host header templates) + `build_credential_map` (host-side `get_secret` resolver) + `DockerProxy` (mitmproxy addon). The worker never holds the secret; the proxy attaches the header *after the request leaves the worker*. | **Deferred to the sandbox milestone** — it needs an isolated worker to sit in front of; built the canonical way then. NOT env-injection (rejected as a leak vector) and distinct from **Secret-Store Config** above (ADR-0008 §5 + "Future work"). |
| **Model Override** | The optional model id threaded as a Durable Flow input (`model: str \| None`, `run_agent_task(task, model=…)`), overriding **only** the active **LLM Provider**'s model id for that run/replay; `None` falls back to `settings.<provider>_model`. | decode's concrete enabler for what-if **Replay** (ADR-0010 §2, task 067). It never changes the provider — `LLM_PROVIDER` still selects that — so there is no cross-provider swap. Surfaced as `decode run --model` / `decode replay --model`; Kitaru swaps it on replay because it is a flow input. |
| **Fork** | A **Replay** that re-executes a recorded run from an anchor with **exactly one** input changed (typically a **Model Override**) — the "what would have happened" run. | Diffed against a **Baseline Rerun**, not the original observed run, so the single change is isolated (ADR-0010 §6). `flow.replay(exec_id, from_=<cp>, model=…)`; the changed run in the "three runs, not two" model. |
| **Baseline Rerun** | A no-change **Replay** from the same anchor as a **Fork** — the *control* that proves the run reproduces faithfully before any difference is attributed to the change. | The middle of the "three runs" (Observed → Baseline Rerun → Fork). If it does not reproduce the observed run (nondeterminism), a diff built on it is untrustworthy (ADR-0010 §6). `kitaru executions replay <id> --from <cp>` with no `--args`. |
| **Checkpoint Override** | A replay override (`--overrides '{"checkpoint.<name>":<value>}'` / `overrides={…}`) that substitutes a recorded **Checkpoint**'s single output at its direct consumers, re-executing from those consumers forward. | The shipped stand-in for mocking a tool's output on replay; per-tool-call `output=`/`raise_=` mocks are **Kitaru roadmap, not shipped** (ADR-0010 §6). Keys must start with `checkpoint.`; other prefixes raise `KitaruUsageError`. Distinct from a **Model Override** (a flow input, passed via `--args`). |
